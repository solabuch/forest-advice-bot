# Бот порад для звірів лісу

Telegram-бот для мешканців лісу Мишки-шкряботушки. Звірі надсилають документи з порадами, інші питають звичайним текстом і отримують відповідь лише з документів — з назвою документа-джерела, а для порад від звірів ще й з ім'ям того, хто надіслав, і датою.

> **Скільки внесок під дубом і до якого числа?**
>
> Внесок — 4 жолуді з дорослого звіра на місяць. Здавати його потрібно до 10 числа. Внески віддають Кабанові в кошик біля входу. Замість 4 жолудів можна віддати 2 лісові горіхи. — з документа «Членські внески» рукавички «Під дубом»

Це справжня відповідь бота на еталонне питання з розмови з Мишкою (див. [requirements.md §4](docs/requirements.md)).

- «Лісовий архів» (78 документів, з них 19 сканів) — у боті з першого старту й синхронізується з Google Диском.
- Документи — PDF (зокрема скани, OCR), Word (.docx, .doc), .rtf, .odt, .txt, .md, будь-якою мовою.
- Кожна порада — лише з доречного місця: рукавичка → вона, її частина лісу й увесь ліс; конкретніша — першою.

## Швидкий старт

Потрібен лише Docker (Compose v2).

1. **Токени.** Створи бота в [@BotFather](https://t.me/BotFather) (`/newbot`) і ключ на [console.groq.com/keys](https://console.groq.com/keys). Потім:
   ```sh
   cp .env.example .env    # Windows: copy .env.example .env; впиши два токени
   ```
2. **Запуск:**
   ```sh
   docker compose up -d
   docker compose logs -f app   # чекай «Бот @… готовий»
   ```
   Compose спершу тягне готовий multi-arch образ (amd64, arm64) з GHCR; не вийшло — збирає локально. Міграції застосовуються самі. На старті бот перевіряє БД, OCR, токен Telegram і ключ Groq і пише, чого бракує, одним реченням.
3. **Напиши боту.** Бот — лише для мешканців (за запрошенням). Хто перший напише свіжому боту, той і стає першим мешканцем. Посилання для інших — `/invite` у боті або в лозі:
   ```sh
   docker compose logs app | grep Запрошення
   ```

Архів імпортується у фоні: текстові документи шукаються за секунди після старту, скани — приблизно за пів хвилини.

## Перевірка за 5 хвилин

**Питання до архіву** — одразу після старту:

| Питання | Що перевірити |
|---|---|
| Скільки внесок під дубом і до якого числа? | Еталон: число, строк, кому, куди, заміна; «хто не платить» не додано |
| Скільки жолудів за місяць платить під дубом родина з трьох дорослих і поросяти? | Розрахунок з правилом: 3 × 4 = 12, поросята до року не платять |
| Які гриби ростуть під вербою? | «Під вербою» — у двох частинах лісу: порада рукавички першою, далі — частини |
| Чим утеплити рукавичку в ліщині? | Окремої поради немає — бот прямо каже, що дає загальнішу (листяного лісу) |
| Чи можна сьогодні перейти брід вище греблі біля річки? | Бот знає сьогоднішній день тижня й називає умови, яких не може перевірити |
| Скільки внесок під дубом і біля мурашника? | Два місця — дві відповіді, кожна зі своїм джерелом |
| Хто голова ОСМД в лішині? | Описка в назві місця — бот усе одно розуміє «У ліщині» |
| Скільки внесок? → потім «А до якого числа?» | Місце кнопками; уточнення бере місце з попереднього питання й каже це |
| Скільки коштує квиток на літак під дубом? | Чесне «не знайшов» — питання потрапляє в `/unanswered` |

Під відповіддю — кнопки з документами-джерелами (бот надсилає сам файл) і «Корисно» / «Хибно».

**Документи** з [`examples/`](examples/) — надішли файлом; що має відповісти бот, описано в [examples/README.md](examples/README.md):
- новий варіант архівного документа → «Так, замінити» / «Ні, це окремий документ»;
- документ без місця → кнопки місць; з незнайомою рукавичкою; для двох місць → «розділи»;
- скан, .doc, .docx з таблицею, .odt, .rtf, .md і документ англійською.

**Команди:** `/places`, `/docs` (документи місця), `/my` (свої з видаленням), `/subscribe`, `/unanswered`, `/wrong`, `/stats`, `/rename`, `/forget`, `/invite`.

## Вимоги

Повний реєстр — [docs/requirements.md](docs/requirements.md): вимоги з розмови з Мишкою ([транскрипт](docs/transcript.txt)), припущення, понад 40 рішень разом із нею і журнал її відповідей. Що з цього перевіряє який тест чи eval-кейс — [docs/traceability.md](docs/traceability.md) (генерується з тестів).

Головне простими словами:

1. Відповідь — лише з документів лісу, з документом-джерелом. Нічого не знайшлося — бот так і каже й не вигадує.
2. Документ стосується рівно одного місця. Незрозуміло — бот питає автора, а не вгадує; кілька місць — просить розділити.
3. Питання про рукавичку — поради її самої, її частин лісу й усього лісу; про частину — частини й лісу; про ліс — лише лісу.
4. Конкретніша порада — першою, загальна — окремо й зі своїм джерелом. Поради одного рівня різняться — обидві, з позначкою.
5. Підпис: архів — назва документа; від звіра — ще ім'я й дата; великий документ — ще розділ і сторінка.
6. Новий варіант документа замінює старий лише після підтвердження; попередній автор дізнається. Видалив новий — знову діє попередній.
7. Ім'я бот питає один раз, при першому документі; без справжнього імені документ не приймає.
8. Місце бот бере з тексту питання — з відмінками, побутовими назвами й описками. Немає — кнопки; уточнення протягом 30 хвилин — місце з попереднього питання.
9. Бот знає сьогоднішню дату: застосовує до неї поради, рахує на прохання й попереджає про минулий строк.
10. «Лісовий архів» — у боті з першого старту й синхронізується з Диском приблизно кожні 15 хвилин.
11. Лише мешканці (за запрошенням) і лише особисті повідомлення: «в лісі бувають мисливці».
12. Адмінів немає: усі звірі рівні — списки й статистика доступні кожному, без імен.

## Як це працює

```text
Telegram ⇄ aiogram 3 (long polling) — middleware доступу → тонкі хендлери
  ingest : файл → перевірки → розбір (+ OCR) → місце (фраза-адресат → LLM → кнопки)
           → новий варіант? → фрагменти → embeddings → чинна версія
  ask    : питання → місце (словник назв → LLM → кнопки) → доречні місця (DAG)
           → гібридний пошук серед чинних версій → LLM лише з фрагментів → підписи кодом
  worker : черга задач у Postgres (розбір, індексація, сповіщення, синхронізація архіву)

Postgres + pgvector — документи й версії, фрагменти з векторами й tsvector, черга, журнал
Локально в образі — multilingual-e5-small (ONNX), Tesseract (ukr + eng), antiword
Groq — qwen3.8-27b → gpt-oss-120b → gpt-oss-20b (fallback за лімітами)
```

На чому тримається правильність відповідей:
- **Область місця — фільтр у SQL**, а не прохання до моделі: фрагмент з чужого місця чи замінений варіант до моделі просто не доходить.
- **Підпис збирає код** з метаданих фрагментів, які модель позначила як використані; номер джерела звіряється зі знайденими — вигадати джерело неможливо.
- **Документи — дані, не інструкції**: фрагменти в промпті екрановані, «вказівки» в документі модель ігнорує.
- **Пошук — гібридний**: два вектори (питання цілком і без назв місць) плюс слова з префіксами для відмінків, RRF. Короткий документ іде у відповідь цілком.
- **Стан діалогу — у БД**: кнопки несуть id, рестарт посеред вибору місця нічого не губить.

## Рішення

Кожне — в окремому ADR у [docs/adr/](docs/adr/README.md) з альтернативами й наслідками. Коротко:

| Тема | Рішення | Чому не інакше |
|---|---|---|
| Сховище | Postgres + pgvector — одна БД для всього | Окрема векторна БД — синхронізація при заміні й видаленні документів |
| Пошук | Гібрид dense + слова з фільтром області в SQL | Лише вектори слабкі на іменах і числах («Кабан», «4 жолуді») |
| Embeddings | Локальна multilingual-e5-small в образі | Зовнішній API — ще один ключ і мережа на кожне питання |
| LLM | Groq, ланцюжок із трьох моделей за живим порівнянням | Одна модель — бот стає при першому 429 |
| Місце документа | Фраза-адресат → LLM → кнопки автору | Пошук назв місць по тексту падає на пастках архіву («сосни», «верба») |
| Місце питання | Словник назв з відмінками й описками → LLM → кнопки | Лише LLM — витрата лімітів на кожне питання |
| Архів | Знімок у репо й образі + синхронізація з публічної теки Диска | Drive API — ключ від рев'юера |
| Черга | Таблиця `jobs` (`SKIP LOCKED`) | Redis/Celery — зайвий сервіс |
| Доступ | Запрошення: перший звір — мешканець, далі — за посиланням | Список id — потрібен адмін, а адмінів немає |
| Тести | E2E всередині процесу: справжній Dispatcher і БД, фейковий Bot API | Живий Telegram у CI — флакі й секрети акаунта |

## Якість і швидкість

[`eval/qa.yaml`](eval/qa.yaml) — 49 кейсів на справжньому архіві й Groq: еталон, розрахунки, скани, пастки архіву («Під вербою», «На узліссі»), конкретне проти загального, «сьогодні», минулий строк, кілька місць, описки, «не знайшов», новий варіант від звіра, документ англійською. Кожне джерело кожної відповіді автоматично звіряється з областю місця й чинністю версії.

| Метрика | Перший повний прогін (48 кейсів) | Ціль |
|---|---|---|
| Джерела з чужого місця чи неактивної версії | **0** | 0 |
| «Не знайшов», коли поради немає | **3/3** | 100% |
| Місце з питання | 48/48 | — |
| Потрібні документи серед знайдених | 40/43 | — |
| Ключові факти у відповіді | 68/80 | ≥ 95% |
| Час відповіді, медіана | ≈ 1 с | — |

Eval знайшов п'ять вад — пошук не бачив назв документів, не знаходив інші форми дієслів, модель брала лише перший пункт переліку, казала «не знайшов» при загальнішій пораді й не помічала минулого строку. Після виправлень із 14 кейсів, що падали чи чутливі до правок, пройшли 13.

Час: зазвичай 1–2 с. Вузьке місце — ліміт Groq free tier: 8000 токенів за хвилину на модель, тобто 2–3 відповіді на хвилину на модель. Коли питання йдуть потоком (як у eval), відповідь чекає ліміту до ~40 с — бот попереджає звіра про затримку.

```sh
docker compose run --rm --entrypoint python app scripts/eval_qa.py   # усі кейси
docker compose run --rm --entrypoint python app scripts/eval_qa.py fees-reference
```

Один повний прогін — ≈150 тис. токенів, приблизно чверть добового ліміту трьох моделей, тож у CI eval лише вручну. Усе, що eval пише в БД, відкочується.

## Обмеження

- **Виключити мешканця не можна** — адмінів немає за вимогою. Якщо посилання-запрошення злили, заміни `INVITE_CODE` у `.env`: старе посилання перестане діяти, мешканці лишаться.
- **Ліміти Groq free tier** — головний ризик під навантаженням: ланцюжок моделей, кеш однакових питань і черга з попередженням його пом'якшують, але не прибирають.
- **Файли до 20 МБ** — ліміт Telegram Bot API для ботів. Локальний Bot API server (файли до 2 ГБ) не зроблено.
- **Лістинг Google Диска без API-ключа** — неофіційний ендпоінт. Не впізнав сторінку — бот нічого не прибирає й працює зі знімком.
- **Пам'ять уточнень (30 хв) — у процесі**: після рестарту бот просто перепитає місце кнопками.
- **Один екземпляр бота на токен** (long polling): другий екземпляр з тим самим токеном пише про це в лог і зупиняється.

## Розробка

```sh
uv sync                 # залежності (Python 3.13)
uv run poe db           # Postgres з pgvector на 127.0.0.1:5432
uv run poe model        # модель embeddings у .data/models
uv run poe check        # ruff + mypy --strict + тести
uv run poe eval         # eval відповідей (Groq)
uv run poe trace        # оновити docs/traceability.md
```

Інтеграційні тести потребують окремої БД: `TEST_DATABASE_URL=postgresql://…` (без неї локально пропускаються, у CI — падають).

- **Тести** — понад 400: unit, інтеграційні на справжньому Postgres (пошук, версії, черга, парсери, OCR), наскрізні через Dispatcher (кожен діалог бота).
- **CI** на кожен PR: ruff, mypy, тести з Postgres, gitleaks, pip-audit, збірка образу з самоперевіркою в контейнері, Conventional Commits у назві PR.
- **Процес** — GitHub Flow: кожна задача — PR із зеленим CI, squash merge; release-please веде [CHANGELOG](CHANGELOG.md) і релізи; після merge у `main` — образ у GHCR.

```text
src/forest_bot/
  handlers/   Telegram: завантаження, питання, документи, підписки, ім'я, статистика
  ingest/     розбір, OCR, місце документа, фрагменти, індексація, архів і Диск
  qa/         місце в питанні, гібридний пошук, відповідь, підписи
  llm/        клієнт Groq з лімітами й fallback, промпти
  repo/       робота з БД
  data/places.yaml  місця лісу: назви, синоніми, частини (правиться без коду)
data/archive/ знімок «Лісового архіву» з маніфестом
examples/     документи для перевірки сценаріїв завантаження
eval/         кейси eval; docs/ — вимоги, ADR, трасування, транскрипт
```
